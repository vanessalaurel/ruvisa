# 2.5 Agentic System

Ruvisa includes an end-to-end agentic layer that can be triggered when the user asks questions such as "What product is recommended for my skin now?" or "How has my skin changed over the past 3 months?". In this system, the FastAPI backend [38] routes the user request to the conversational agent through the `invoke_agent(...)` method, which is **defined in this work**. For reasoning, the system uses a locally hosted Ollama large language model runtime [40], while the overall agent flow is organized as a ReAct-style [6] LangGraph workflow [39].

This design allows the platform to go beyond static recommendation output. Instead of returning only a ranked list of products, the system can interpret natural-language questions, inspect the current user state, call recommendation and tracking functions when needed, and then generate a grounded response based on the latest available evidence. In this way, the agentic layer acts as the interface between the user, the recommendation engine, and the longitudinal skincare-tracking components.

## 2.5.1 Agentic Architecture Overview

The conversational layer is implemented as an agentic orchestration module that connects the frontend chat interface, the FastAPI backend [38], the local Ollama runtime [40], and the internal recommendation and tracking tools. In practice, when a user submits a request such as "What product is recommended for my skin now?" or "How has my skin changed over the past 3 months?", the FastAPI `/chat` endpoint forwards the message to the agent through the asynchronous `invoke_agent(...)` method (**defined in this work**).

The agent is built using a ReAct-style reasoning-and-acting pattern [6] implemented through LangGraph [39]. A locally hosted Ollama model [40] is used as the reasoning engine, with the runtime configured around the `llama3.2:latest` model, a local base URL, and a low temperature setting to keep responses more stable and consistent. The graph is initialized with three main inputs: a fixed system prompt that defines the agent's role and tool-use rules, a set of domain-specific tools, and the current user message enriched with database-derived user context.

This architecture allows the agent to decide whether it can answer a question immediately or whether it first needs to call one or more tools. As a result, the conversational system does not rely only on free-form language generation. Instead, it combines LLM reasoning with deterministic program logic, allowing recommendations and progress summaries to remain grounded in the actual Ruvisa pipeline. The overall orchestration strategy is therefore informed by prior work on reasoning-and-acting agents [6] and graph-based agent runtimes [39], while the exact tool inventory, prompting policy, and recommendation logic are **defined in this work**.
